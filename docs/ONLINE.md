# TouchLine online layer

The optional online layer: accounts, cloud saves, the verified Daily board, the world leaderboard (the weekly fixed-seed challenge, all-time Daily totals and best streaks, Quick Draft's 38-0 chase on server-issued wheels, a country filter on every board), challenge short codes and, in Phase 2, online head-to-head rooms (section 5e). **Live on https://touchline.quest since 2026-10-26**: the Render live site carries `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, every migration below is applied, and `touchline-e4` is deployed (section 5a). The full build plan, with every decision and the reasons for it, was written for the implementation agents on 2026-10-25 (the "online build plan"); this page is the short version that lives in the repository, plus the runbooks.

## 1. Shape in one paragraph

The game stays offline-first and unchanged. `src/online` loads only when the build carries both `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (`onlineConfig()` is null otherwise, and `main.tsx` never imports `./online/boot`). Clients write only their own private rows (cloud saves, the synced profile, their display name and country, challenge codes). Everything shared or competitive (Daily and weekly entries, all-time totals, 38-0 chase attempts and runs, head-to-head rooms) is written only by one Edge Function per engine version, `touchline-e{ENGINE_VERSION}`, which replays the posted picks with the game's own engine on the data version they were played on. A posted score is never stored as a score: the server's replay is the official result.

This project's default privileges grant every new table, sequence and function in `public` to `anon` and `authenticated` (read from `pg_default_acl` on 2026-10-25). Every migration therefore revokes table privileges and EXECUTE before granting, the stand-in mirrors those defaults, and the suite asserts that `anon` can read only `daily_puzzles` and `weekly_puzzles` and execute only the ten readers (the eight Phase 1 readers plus `chase_board` and `chase_summary`).

Every board function takes an optional country (`p_country`, ISO 3166-1 alpha-2 such as `GB`, `VN`); with it the board, the positions and the counts are those of that country only. The country, like the display name, is copied onto each board row when it is posted, so the public never reads a profile and a later change never rewrites history.

Rules that hold across all of them: RLS on every table in `public` and `private`; no SECURITY DEFINER function in `public`; `search_path` pinned everywhere; `svc_*` functions executable by `service_role` only; `anon` can execute exactly `daily_board`, `daily_summary`, `daily_rank`, `daily_alltime_board`, `weekly_board`, `weekly_summary`, `weekly_rank`, `get_challenge`, `chase_board` and `chase_summary`, plus Phase 2's `h2h_peek`. Picks, XIs and payloads on a board stay hidden until nobody can post that day or week any more.

Run the SQL suite locally with `npm run sql:test` (needs PostgreSQL 16 or 17 binaries; `PG_BIN=/usr/lib/postgresql/16/bin` by default, or `DATABASE_URL` for an existing empty database). It prints `PHASE 1 ASSERTIONS PASSED`, then `REVIEW ASSERTIONS PASSED` and `REVIEW 2 ASSERTIONS PASSED` for `supabase/tests/sql/phase1_review.sql` (the attacks a hostile client tries: null base revisions, another account's rows and objects, direct writes to boards, pins and totals, private helpers called directly, look-alike names, impossible figures), `SECURITY ALLOWLIST ASSERTIONS PASSED` for `phase1_security.sql` and `CHASE ASSERTIONS PASSED` for `phase2_chase.sql` and `ROOMS ASSERTIONS PASSED` for `phase2_rooms.sql`: a migration that exposes a new function must add it to that file's lists on purpose. The throwaway cluster is UTF8, as Supabase is; the review suite refuses to run on any other encoding, since a SQL_ASCII cluster tests the name rules on bytes.

## 5. The weekly challenge

- One puzzle per ISO week (Monday 00:00 UTC to the next Monday), seed `weekly-YYYY-Www` (`weekKeyOf(date)`), settings from `weeklyGameSettings(u, key)` in `src/online/weekly.ts`: an England wheel (the Daily's), a complete English season, host club and formation chosen by hashing the week key, the Daily's rules and season options (`DAILY_RULES`, `DAILY_SEASON`: the Daily's re-spins, two by the owner's decision, twists, the January window, no Continental Cup run). The verifier never holds a re-spin count of its own: it replays `DAILY_RULES`. It is played as a Quick game; changing the mapping changes that week's puzzle for everyone, so treat it like the Daily mapping.
- Verified exactly like the Daily (`verifyWeekly`): the strict draft replay, then the quick season, figures from the replay only.
- First post stands (like the Daily): one entry per account per week; posts accepted until 00:00 UTC on the Tuesday after the week (a one-day grace for a run started late on Sunday), picks revealed after that. 2026-W43 is a 4-4-2 diamond as Southampton in 2018-19.

## 5a. The Edge Function (`touchline-e{ENGINE_VERSION}`)

One function per engine version. **Deployed: `touchline-e4`, the loader form, version 5, Verify JWT off, auth `['user', 'publishable']`, pinning `edge/verifier-37d256f009b3b3e9.js` (SHA-256 `37d256f0…9b82`), which the live site serves** (2026-10-26, owner-approved; checked live: a guest's `daily.pin` answers 401 "Sign in first"). Engine 5 adds `touchline-e5` (engine `'5'`, `supabase/config.toml` `[functions.touchline-e5]`) and keeps `touchline-e4` at least 7 days; the engine 5 site keeps serving e4's bundle byte for byte so that loader keeps working (section 7, "Release engine 5"). Engine 6 adds `touchline-e6` and keeps `touchline-e5` (and `touchline-e4` to 2026-11-03) the same way, serving both outgoing bundles from `public/edge/` (section 7, "Release engine 6"). Phase 1 deployed it with `verify_jwt` on and `withSupabase({ auth: 'user' })`. **From Phase 2 it is `withSupabase({ auth: ['user', 'publishable'] })`, deployed with `verify_jwt` off** (the platform's check would refuse a guest, who has no JWT, before our code runs): `withSupabase` itself verifies a user's JWT (against the project's JWKS) or the project's publishable key, refuses anything else with 401, and a present but invalid JWT is refused, never read as a guest. A call with a user's JWT is that user; a call with the publishable key alone is a guest, who may call only the `room.*` ops (every other op answers 401 `unauthorised`; `edge.ts` and `service.ts`, tested in `edgeBundle.test.ts` and `rooms.test.ts`). The user id still comes only from the verified claims. The flow lives in `src/online/server/service.ts`; `supabase/functions/touchline/index.ts` only wires it to Supabase. POST a JSON body `{ op, ... }` (at most 16 KB):

| Op | Body | Answer |
| --- | --- | --- |
| `status` | | `{ status: 'ok', engine, live, today, week }` |
| `daily.pin` | `date?` (today or yesterday, UTC) | `{ status: 'ok', pin }`; the first call of the day pins it |
| `weekly.pin` | `week?` (`YYYY-Www`, while open) | `{ status: 'ok', pin }` |
| `daily.submit`, `weekly.submit` | `encoded` (the `ChallengePayload`), `teamName`, `shortName` | 200 `ranked` / `duplicate` / `already_submitted` with `position`, `total`, the country figures and `official` (the replay's figures, `claimMatched`) |
| `chase.start` | `leagueId`, `formationId`, `ratings?` (`season` default, or `prime`), `benchPicks?` (0 default to 5), `engine`, `data` (what the device runs) | 200 `{ status: 'ok', attempt: { code, seed, leagueId, formationId, ratings, benchPicks, engineVersion, dataVersion, createdAt, expiresAt }, left, cap, resetsAt }`; 409 `data_mismatch` (with `liveData`: reload first, no attempt spent) or `engine_mismatch`; 429 `rate_limited` (with `resetsAt`) after five attempts in a UTC day |
| `chase.submit` | `encoded`, `teamName`, `shortName` | as the boards' submit, with `key` (the attempt code), `position`/`total` (all time), `week`, `weekPosition`/`weekTotal`, `perfect`, `games`, `personalBest`; 409 `no_attempt` (not this account's wheel), `closed` (48 hours passed) |
| `account.delete` | `confirm: 'delete my account'` | removes every object under `saves/<uid>/`, revokes every session, deletes the user (foreign keys remove the rest) |
| `room.create` (guests too) | `settings` (`leagueId`, `wheelLeagues`, `leagueSeason`, `difficulty`, `hardMode`), `manager` (`name`, `formationId`, `hostClubId`), `engine`, `data` | `{ status: 'ok', seat: 0, token, room }` |
| `room.join` (guests too) | `code`, `manager`, `engine`, `data` | `{ status: 'ok', seat: 1, token, room }` (the draft has started) |
| `room.pick` (guests too) | `code`, `token`, `version`, `playerSeasonId`, `slotId` (a slot id or `bench`) | `{ status: 'ok', room }` |
| `room.leave` (guests too) | `code`, `token` | `{ status: 'ok', room }` (status `left`) |
| `room.resume` (accounts only) | `code` | `{ status: 'ok', seat, token, room }`: the signed-in account's seat with a new token |

Errors are `{ status, code, reason, ...context }` with these HTTP statuses: 400 `bad_request`; 403 `guest`; 409 `closed`, `no_puzzle`, `no_attempt`, `engine_mismatch` (with `pinnedEngine` or `liveEngine`), `data_mismatch` (with `pinnedData`), `puzzle_mismatch`; 422 `invalid_payload`, `invalid_team`, `invalid_picks` (the replay's reason, "Spin 4: ..."); 429 `rate_limited` (per account per hour: 20 posts per board, 30 pins, 12 chase starts, 5 deletions; and five chase attempts per UTC day; per account or guest per hour: 30 rooms made, 60 joins, 900 picks, 60 leaves, 30 resumes); 503 `live_build_unavailable`, `packs_unavailable`, `unavailable` (safe to retry). The rooms add 401 `unauthorised` (a guest on any other op, `room.resume` signed out), 403 `not_seated`, 404 `no_room`, 409 `room_closed` (with `roomStatus`), `room_full`, `not_your_turn`, `stale` (the room moved since the version sent), 422 `invalid_room`, `invalid_manager`, `invalid_pick` (the engine's reason) and 503 `rooms_busy` (300 rooms open at once). Challenge codes have no op: `create_challenge` and `get_challenge` are database functions.

- **Pins.** A pin is made at most once per day or week, only by the live engine: the function reads `<TOUCHLINE_SITE_URL>/build.json` (cached 5 minutes per isolate; a run on a data stamp the cached copy does not name rechecks it first, and fetches, failed ones included, are at most one per 30 seconds per isolate) and refuses with `engine_mismatch` when the live site runs another engine. The settings come from `dailyGameSettings` / `weeklyGameSettings` on the England universe of the live data stamp.
- **Packs.** The first time a stamp is seen live, the function fetches `data/leagues.json` and every league's `players.json` and `meta.json` from the live site, checks the stamps, hashes each file (SHA-256), uploads them to the private bucket `packs` at `v/<stamp>/...` (never overwriting) and registers the hashes (`svc_register_data_pack`). Universes are built only from the archive, each file checked against its hash, two kept per isolate.
- **Data versions.** A run on the pin's data ranks; a run on a stamp the live site served after the pin was made (a mid-day rebuild) ranks on its own data; anything else is `data_mismatch`.
- **Secrets.** `TOUCHLINE_SITE_URL` (default `https://touchline.quest`). The platform injects `SUPABASE_URL`, the publishable and secret keys and the JWKS; nothing else, and no key is in the repository.

## 5d. The 38-0 chase (Quick Draft's world leaderboard)

The owner's goal: "the goal for Quick Draft is 38-0, the flawless season", with "a world leaderboard … 38-0 chase". A signed-in player's standard Quick Draft season goes to the chase with its challenge link, the server replays it with the verifier, and the board ranks the replay's points, W-D-L and goal difference.

**The anti-grinding rule: server-issued attempts.** A Quick Draft seed is the player's own, so a board of player-seeded seasons rewards whoever grinds seeds offline (spin, look, start again) until the wheel deals a lucky run; no amount of server replay can tell a ground seed from a fair one. So the chase ranks only seasons played on a wheel the server dealt: World > 38-0 chase > "Start a chase run" calls `chase.start` with the league, shape, player ratings (Season or Prime) and bench (0 to 5) the player picked; the database draws a random 10-character code (`private.random_code(10)`, about 50 bits) and the game starts at once on seed `chase-<code>`. Each account gets **five attempts per UTC day** (`private.chase_daily_cap()`, `CHASE_ATTEMPTS_PER_DAY`), each **open 48 hours** and **posted at most once** (the first post of an attempt stands: a retry is `duplicate`, another draft `already_submitted`). An abandoned attempt still counts against the day, so dropping a bad first spin costs a run. The attempt belongs to the account that drew it: the code is looked up with the JWT's user id, so a lucky wheel cannot be passed to another account, and a seed the server never issued is `no_attempt`.

Trade-offs considered:
- *A fixed weekly or daily chase seed* (like the weekly challenge): honest, but it is the same wheel for everyone, so the board becomes a puzzle to rehearse (the weekly already is one), and with any free choice left (league, shape) the player can still grind those offline. Server-issued attempts keep the Quick Draft feeling (your own wheel every time) while bounding the luck anyone can buy to five draws a day.
- *Player seeds with a cap on submissions*: a cap limits posts, not offline grinding, so it would not be honest.
- *What remains possible*: a player can replay one issued wheel offline with different picks before posting (as with the Daily, where picks are the skill) and can hold several accounts (one account per person is the fair-play rule; accounts need an email). Five draws a day per account is the luck budget; the Summary's Submit is explicit, so a weak run need not be posted, but its attempt is spent.

**What a chase run is** (`chaseGameSettings`, `src/online/chase.ts`; treat it like the Daily mapping, since changing it moves every open attempt): the standard Quick Draft (`CHASE_RULES`: `QUICK_RULES` written out, normal difficulty and its one re-spin, ratings shown, Squad First, the all-time wheel of the league played in, twists on, the plain manager pick), calibrated opposition, the January window, no Continental Cup run, the league, shape, ratings and bench chosen at issue (stored on the attempt: `ratings`, `bench_picks`), a complete real season chosen by `hashString('chase-' + code)` and the side replaced chosen as Quick Draft chooses by default (`defaultHostClub`, mid-table). **Season and Prime ratings both count**, and so does **a bench of 1 to 5** (both are standard Quick Draft choices; Setup's Quick Draft now starts on Prime and a bench of 1, so the start card offers that first, `CHASE_DEFAULT_OPTIONS`, and the board ranks every combination together, showing "Prime" beside the league and the bench in the tooltip). The verifier replays a bench exactly: `strictReplayDraft` now allows the bench places in its row cap (squad size + bench + re-spins + 1) and replays a bench closed early, with or without a spin showing (`closeBench`); the season's bench changes and injury cover were already replayed (`x.s`). Without bench places, as on the Daily and weekly, nothing changes. **The plain manager pick counts**: it is in every standard Quick Draft (`QUICK_RULES.managers`), chooses among the real managers of the club-seasons drafted, draws nothing and replays exactly (`x.m`). Kept off, as on the ranked boards: modes, the Upgrader, power-ups and the locker, the Super League, the **manager spin**, the end-of-draft case and its Icon, classic seasons, the salary cap and the teammate chain (`CHASE_NON_STANDARD_RULES` = `NON_STANDARD_RULES` less `managers`). A **January-window gamble** (the spin or Upgrader in the window, built on another branch) is non-standard until the verifier replays it: that change must add its refusal to `nonStandardRun` (every board) and `chaseUnrankedReason`, or the strict replay would drop it and rank a different season from the one played.

**Verifying.** `chase.start` refuses a device whose engine or data differ from the live site's (409, "reload", before an attempt is spent) and archives the live data first. `chase.submit` decodes the payload, finds the caller's attempt by the seed's code, checks it is open, then `verifyChase` rebuilds the attempt's settings on the payload's data (the attempt's own, or a stamp the live site served after the attempt was issued) and runs `replayVerdict`, the same strict draft replay and exact season the Daily and weekly use. The posted claim is only compared (`claimMatched`).

**The board** (`chase_board`, `chase_summary`): each account's best run, this ISO week (the week the attempt was issued in) or all time, with the country filter. Order: points dropped against the league's maximum (3 a game), then fewer defeats, goal difference, goals scored, first posted. Within one league that is simply points then goal difference; across leagues it lets a Bundesliga 33-1-0 (100 of 102) stand above a Premier League 32-4-2 (100 of 114). A flawless season (every league game won: 38-0, or 34-0 in an 18-club league) is flagged with a green "Flawless 38-0" chip, and the board's head carries the closest-ever-to-perfect record. Payloads are public at once ("Race": a challenge link, never ranked): a chase seed is personal and single-use, so racing a posted run helps nobody rank.

**In the app** (an online build only): World > 38-0 chase (the side panel's This week / All time, the country filter, "Start a chase run" with League, Shape, Ratings and Bench and "3 of 5 runs left today"; the board with W-D-L in green, amber and red, the flawless chip, the record line and your place pinned at the foot); the Quick Draft Summary's `ChaseStatus`: "Submit to the 38-0 chase" on an eligible chase run (it files the run in the outbox as kind `chase`, closing with its attempt, and posts it signed in), then "On the 38-0 chase: 3rd of 120 all time · 1st of 9 this week"; any other Quick Draft says why it is not on the chase. Chase runs are never filed on their own, so the Daily and weekly capture is unchanged.

## 5e. Online head-to-head rooms (Phase 2)

Shipped in PR #61 and live since 2026-10-26 (`h2h_rooms` applied, `touchline-e4` deployed with Verify JWT off). The game rules are in `docs/GAME_DESIGN.md` section 18.

- **Shape.** Two managers, two devices, one wheel: the hot-seat head-to-head (`src/engine/h2h.ts`, `runH2HSeason`), replayed by the server. A room is a row of `private.h2h_rooms`: an 8-character code (the challenge-code alphabet; the link is `#h=K7Q2MX9A`, which `codes.ts` reserved in Phase 1), a random seed (`room-` and 12 characters, made in SQL), the settings, the two managers, the public log (`events`: `{ t: 's', cs: 'clubId@season' }` for a spin, `{ t: 'p', seat, p, k }` for a pick), whose turn it is, a version, the season once played, the engine and data versions, and the deadlines.
- **No account needed.** Anonymous sign-ins stay off, so a guest never holds a JWT: the Edge Function accepts the publishable key alone for the `room.*` ops (section 5a). A seat is a token the server makes (`randomToken`: 32 random bytes, base64url) and hands out once, in the answer to `room.create` or `room.join`; the database keeps only its SHA-256 (`seat0_hash`, `seat1_hash`), and every later call proves the seat with the token (the server hashes it; the SQL compares). The device keeps the token in `localStorage['touchline-rooms-v1']` for two days. A signed-in manager's account is kept on the seat (`seat0_user`, `seat1_user`, `on delete set null`), so `room.resume` can give them a new token on another device (the old one stops working). Guests are metered by `guestSubject`: a UUID made from a SHA-256 of the first `x-forwarded-for` address (with a fixed prefix), never the address; logs say `guest`.
- **The server's replay is the room.** Every `room.pick` reads the row with its seed (`svc_h2h_room_get`), finds the seat from the token, refuses when the room is not drafting, the version is not the one the client saw (`stale`) or it is the other seat's turn, then replays the whole room from the seed (`roomPick`: each stored spin recomputed and compared, each stored pick applied by the engine), applies the new pick with the engine's own checks (`invalid_pick` with its reason), spins on until someone must pick (`spinUntilPick`) and, when both squads are complete, plays the season (`runH2HSeason`). It files the new log entries, the next turn and the result with `svc_h2h_room_move`, which checks the token hash, the turn, the version and that the entries start with that seat's pick (a compare-and-set: two devices cannot both move). A stored log that does not replay (never the player's fault) is a 503 and a log line `room_replay_failed`. `room.join` replays the start the same way (`roomStart`) and files the first spins with seat 1.
- **Data and engine.** A room plays on the data the live site served when it was made (`room.create` refuses a client on any other stamp or engine with `data_mismatch` / `engine_mismatch`, "reload the game"), and a joiner must be on the same stamp. The server builds the universe of the room's leagues from the pack archive (section 5a), cached two per isolate; the whole seven-league wheel replays a pick in well under a second warm (`rooms.test.ts`).
- **The seed is secret until the end.** The public view (`private.h2h_room_json`) carries the log, never the seed, until the room has finished, so nobody can work out the next spin; the clients rebuild the draft from the log with `draftFromEvents` (the engine's `h2hLand`, no RNG). The finished view carries the seed and the season, so anyone can replay it hot-seat and compare (`check:verifier` does).
- **Live updates: polling, not Realtime.** The two devices read the room with `public.h2h_peek(p_code, p_since)`, a plain PostgREST RPC (anon and authenticated), every 2 s while the other manager picks, 3 s in the waiting room, 6 s on your own turn (to see a leave or a timeout) and 15 s in a hidden tab, stopping once the room ends (`pollDelay` in `src/online/rooms.ts`). With `p_since` equal to the room's version it answers `{ unchanged, version, status }`, a few bytes. Why not Realtime: Postgres Changes needs the table in an exposed schema with a SELECT policy for `anon`, which would expose every room (seeds and seat hashes included) to anyone subscribing with a filter of their choosing, and private Broadcast channels need an authenticated user, which a guest is not; both would also put state outside the server-checked path. Why not the Edge Function for reads: invocations are the Free plan's metered resource (500,000 a month), while a PostgREST RPC is one index lookup. A 15-minute draft costs about 450 polls per device and about 25 function calls in all. The poll reveals nothing beyond what the two managers already see.
- **Timing.** A room nobody joins closes 30 minutes after it was made (`expires_at`); a draft with no move for 15 minutes times out (`last_move_at`); a manager can leave at any time (`left`). Readers and writers apply both deadlines at once (`private.h2h_room_status`, `private.h2h_room_settle`), and the pg_cron job `touchline-h2h-rooms` (every 10 minutes) files them and deletes every room 24 hours after it ended (`private.h2h_rooms_sweep`). The figures are on the Privacy page (`RETENTION`, pinned to the SQL and the client by `retention.test.ts`).
- **Limits.** At most 300 rooms open at once (`rooms_busy`); per account or guest per hour 30 rooms made, 60 joins, 900 picks; a log of at most 160 entries; settings 2 KB, a manager 512 bytes, the season 64 KB.
- **Offline.** With `VITE_SUPABASE_*` missing the Play online switch is not rendered, a `#h=` link says "Online rooms need the online version of TouchLine", and the hot-seat setup, draft and result are exactly as before.

## 5f. Error reports (no third-party service)

Built on `claude/r7-error-reporting` (2026-10-27); not live until the migration is applied and the function redeployed (runbook in section 7). An online build reports what breaks to its own Supabase project; no other company sees a report.

- **What is captured** (`src/online/errors.ts`, started by `boot.ts`, so an offline build has none of it): `window` `error` (uncaught errors), `unhandledrejection`, what the screen boundary caught (`ScreenBoundary.componentDidCatch` in `src/ui/lazyScreens.tsx` calls `signalError` in `src/online/core/errorSignal.ts`, an import-free event with a five-entry buffer for errors before the reporter starts) and chunks that did not load (the boundary's `isChunkLoadError`, and Vite's `vite:preloadError`). Ignored: a cross-origin "Script error.", the browser's "ResizeObserver loop" notice, and a chunk failure while the device is offline (the offline card's job).
- **What a report holds** (`ErrorReport` in `src/online/core/errorReport.ts`): `kind` (`error`, `rejection`, `boundary`, `chunk`), the message (300 characters) and our own stack frames (`trimStack`: only frames on the page's origin, reduced to path and position, at most 8), both scrubbed (`scrubText`: emails, JWTs, `sb_` keys, long tokens, every URL query and hash, so a `#c=` draft or an auth redirect never travels); the build id (`builtAt` of the page's `build.json`, `dev` in the dev server); `ENGINE_VERSION`; the store's `screen` and `game.phase`; the viewport; a browser and OS family (`uaFamily`: `safari/ios`, never the user agent or a version); the device's error-report id (a random UUID in `touchline-online-v1`'s `errors.id`, made for reports alone, not the sync record's `deviceId`); a count and when it was first seen. Never game data, an account id, an email, a token or an address.
- **Per device** (`admit`, `afterPost`): the same error (kind, message, first frame: `fingerprintOf`) is sent at most once a day, repeats only count; at most 10 reports an hour and 30 a day (`DEVICE_LIMITS`), more are dropped; the queue (at most 20) waits in `touchline-online-v1` while offline or while the server answers 429, 5xx or 404 (back-off 1, 2, 4 ... minutes, at most an hour), and is dropped on a 400, 413 or 422. Batches of 5, four seconds after a capture, on `online`, and eight seconds after a page load.
- **The setting.** Profile > Settings > Error reports (online builds only; per device, `touchline-error-reports-v1` = `off`). Off takes nothing and empties the queue (`errorReportsChanged` in `api.ts`, and the reporter checks before every capture and post).
- **The op** (`errors.report` in `src/online/server/service.ts`): the client posts with the publishable key only, never the session's JWT, so a report is tied to no account; a signed-in caller's reports carry no account id either. `parseRequest` runs `reportProblem` on every report (exact keys, every size, the alphabets, and the scrub again: a report that still holds an email, a token or a URL query is a 400), 1 to 5 reports a call; metered 20 calls an hour per guest subject (the address hash, section 5e) or account. It writes through `svc_error_report` (service_role only), answers `{ status: 'ok', taken }`.
- **The table** (`supabase/migrations/20261027120000_error_reports.sql`): `private.error_reports`, RLS with a deny-all policy, nothing granted to `anon` or `authenticated`; one row per device, fingerprint (`private.error_fingerprint`, an md5 prefix) and UTC day, a repeat adds to `count`; a report breaking a check is skipped; the table takes at most 2000 rows an hour across every device (`private.error_reports_hourly_cap`), then answers 0. Kept 30 days after last seen (`private.error_reports_keep`, the daily pg_cron job `touchline-error-reports` at 04:41 UTC running `private.error_reports_prune()`, owner only). The owner reads `private.error_report_summary` (owner and service_role only; runbook "Read the error reports"). Tested by `supabase/tests/sql/phase3_errors.sql`; the figures on the Privacy page come from `RETENTION` (`retention.test.ts` pins them to the SQL and the client).
- **The verifier bundle.** `service.ts`, `validate.ts` and `edge.ts` changed, and `core/errorReport.ts` is new in the bundle, so the edge bundle's hash changes: the site deploys first, then the loader of the live engine's function (section 7, "Apply the error_reports migration"). Until then the old function answers `Unknown operation` (400) and the client drops those reports; nothing else changes.

`update private.daily_entries set hidden = true where id = ...;` then `select private.daily_totals_refresh(user_id) from private.daily_entries where id = ...;` (same for `private.weekly_entries`, which has no totals).

### Rename an abusive display name
`update public.profiles set display_name = 'Manager ' || private.random_code(5) where user_id = ...;` Board rows keep the name they were posted under; hide them if needed.

### Restore a user's previous save
The player can do it themselves: the Account screen > Cloud saves > Cloud history lists each slot's previous copy (and a game abandoned on another device) with "Restore". If they cannot (the previous copy is the same game, or they ask for help): `select slot, game_id, prev_game_id, prev_object_path, prev_saved_at from public.cloud_saves where user_id = '<uid>';`, download `prev_object_path` from Storage > `saves` in the dashboard, gunzip it (`gunzip -c file.json.gz > game.json`; it holds that slot's compacted game, or the hot-seat state for `h2h`), wrap a game as `{"state":{"game":<game.json>},"version":1}` and send them the file: the Record page's Import reads plain JSON. Import replaces that device's whole save, so they export theirs first. Never write their rows by hand; a hand-edited revision breaks the compare-and-set.

### Delete a user (on request, when they cannot sign in)
1. Storage > `saves`: delete the folder `<uid>/` (Supabase refuses to delete a user who still owns objects). 2. Authentication > Users: find the user by email, Delete user. Foreign keys remove the profile, cloud rows, Daily and weekly entries, totals and challenge codes. 3. A change-log line without the email. A signed-in user does all of this from the Account screen > Delete account (the Edge Function's `account.delete`).

### Rotate keys
- **Publishable key** (public, but rotate after abuse): Settings > API Keys > create a new publishable key; set it as `VITE_SUPABASE_ANON_KEY` on the Render live site and redeploy; update the Vault secret `touchline_publishable_key` (`select vault.update_secret((select id from vault.secrets where name = 'touchline_publishable_key'), '<new key>');`) and the repository variable `SUPABASE_PUBLISHABLE_KEY`; after a day (installed apps refresh on their next visit), disable the old key.
- **Secret key**: Settings > API Keys > create a new secret key, then delete the old one. The Edge Function reads `SUPABASE_SECRET_KEYS` from the platform, so no code or secret changes; call `status` and post a test Daily afterwards. The key is never in the repo, CI or a `VITE_` variable, so nothing else moves.
- **Google OAuth client secret**: rotate in Google Cloud, paste the new secret in Authentication > Providers > Google.
- **Resend API key** (SMTP password): create a new key in Resend, paste it in Authentication > SMTP, delete the old key.
